# Architecture decisions — MVP v0.1

## 1. Single service and durable storage
Use Python 3.12+, a threaded standard-library HTTP server, SQLite, and static HTML/CSS/JavaScript. This keeps the pilot reproducible with a single command. SQLite stores profiles, conversations, achievements, proposals, sessions, and encrypted Google tokens. All private API routes require a session. Google sign-in is restricted to the first account that connects; changing pilot owner requires an explicit database migration. Demo sessions have isolated data and never access Google credentials. Deploy behind an HTTPS reverse proxy; the bundled server is a development server.

## 2. Calendar authority and approval
Google Calendar primary events are authoritative. Fetch current events before every proposal and again before approval. Persist Google event IDs and etags. Creation uses a stable client-generated event ID for retry safety. Rescheduling PATCHes the existing event with If-Match; it never inserts a replacement. Provider failures preserve pending proposals. Pull synchronization reconciles moved/deleted events; local approved writes supply the other direction. The client polls sync every minute and on page focus, rather than requiring public webhook infrastructure. Recurring events expand into instances; Google handles recurrence. This MVP writes single events only. An approval applies only to the exact displayed proposal; corrections invalidate older proposals. API approval is serialized per process. Google offers no transactional availability-and-insert operation, so simultaneous external calendar edits remain a small unavoidable race.

## 3. Interpretation versus constraints
A replaceable interpretation adapter extracts natural language into structured achievements. With AI_API_KEY, use OpenAI structured JSON output; without it, use a deliberately limited English/Hebrew rule parser and disclose the limitation. Missing titles and unsupported recurrence require clarification. Treat all Google events as blocking unless an explicit, structured compatibility annotation exists. Never trust an LLM to waive conflicts, deadlines, time windows, capacity limits or approval. Profile interview extracts preferences; explicit corrections persist as scoped title preferences. Do not generalize a person's availability to all activities.

## 4. Humane scheduling
Search local-time slots over the next seven days, preserving working/personal windows, sleep, a daily unscheduled reserve, a daily commitment limit and buffers. Account for full-day events and timezone offsets. Passive/interruptible resource compatibility is represented explicitly; unannotated external events remain conservative. Capacity exhaustion yields no proposal, not a growing queue. Missed achievements retain their identity and notes; rescheduling keeps the original until a replacement slot is approved. The daily close is opt-in and does not label incomplete work overdue. Advanced displacement chains, travel routing, recurring achievement creation, proactive notifications and autonomous scheduling are deferred.

## 5. Security and secrets
OAuth uses random state bound to an HttpOnly SameSite=Lax session, PKCE, verified Google identity, and server-side refresh tokens encrypted with Fernet. The generated encryption key and database live under ignored .local with owner-only permissions. Keep the key with the database when backing up. No tokens are returned to the browser. Mutating APIs require a per-session CSRF token. Session identifiers rotate on Google login. OAuth redirect origin comes from APP_URL, never request headers. Cookies become Secure when APP_URL is HTTPS. Use Google testing consent mode with only the pilot account. Scopes are openid/email and calendar.events; no service account is required. Do not log credentials or provider response bodies.
